# v0.2.1 release qualification — 2026-11-08

Local source verification passed. Hosted verification and public publication
are pending; their evidence will be recorded after completion.

## Review baseline

The baseline was `46b7a5a7baf4f345f96dee197ecaff3e8c05f11a`. The review
confirmed two defects: AMQP transient capacity could trigger an error Detach,
and a persistent MQTT client could admit a shared subscription that its
checkpoint schema subsequently rejected after SUBACK.

The first local review run had six failures among 1,006 executed ordinary
tests; the 111 independently enabled interoperability tests had eleven
failures, concentrated in persistence/recovery timeouts and MQTT Server
unavailable responses. A focused follow-up retained one MQTT CONNECT receive
timeout. These historical failures are not relabeled as passing.

Before either repair, another run using the unchanged baseline beams passed
the selected TLS timeout test and all thirteen MQTT broker persistence tests.
A separate twelve-sample real WAL append/full-synchronization probe measured
0–9 ms on the local ext4 filesystem. The original failures remain
intermittent observations without a proven per-stage cause; no production
timeout or test assertion is weakened to hide them.

## Repair evidence

Regression tests reproduced the transient AMQP Detach, fragment-slot
exhaustion, permanently impossible send, and MQTT persistent shared-subscribe
admission before the respective repairs. A two-Link regression also reproduced
a pending claim stranded when another Link advanced the Session delivery ID
from zero to one. Sender capacity now reserves the largest unsigned delivery-ID
encoding, keeping that limit stable across constructor boundaries and the
asynchronous capacity-to-send interval.

The repaired behavior is covered by pure capacity/fragment tests and real TCP
broker/client tests for ordered wakeup, permanent refusal, disconnect release,
two-Link progress and absence of repeated queue-event churn. MQTT coverage
checks rejection before allocation/transmission, ordinary operations after
rejection, and unchanged memory-profile shared subscriptions.

The first complete post-repair run passed 1,125 tests with independent peers.
After the delivery-ID boundary regression was added, the next run passed
1,126 tests and reproduced one existing TLS timeout-test race: its 40 ms
accept timer expired during socket ownership transfer, before the handshake
under test began. The observed event was `:accept_timeout`, not the asserted
`{:handshake, :timeout}`. This identifies that test setup race specifically;
it does not establish the cause of the earlier persistence failures.
The fixture now accepts the socket inside a gated initializer and installs its
monitor before starting the handshake. The original 40 ms timeout, exact
handshake-timeout event, normal process exit and closed-socket assertions are
unchanged. All 24 connection tests passed, as did a separate fixture check with
an intentional 80 ms delay before initialization continued.
