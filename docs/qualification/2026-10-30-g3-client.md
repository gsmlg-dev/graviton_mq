AMQP protocol ID 0 path, not a substitute for our own broker.

Independent python-qpid-proton **0.40.0** publishers/receivers validate both
application directions through Artemis:

1. Graviton sends a 160 KB binary body; Artemis returns Accepted and an
   already-attached independent Proton receiver verifies length and SHA256.
   Receiver readiness is observed before sending because the fixture's
   default auto-created multicast address need not retain a message with no
   receiver. Accepted does not imply a business recipient exists.
2. Proton publishes a 100 KB binary body; Graviton advertises an incoming frame
   limit of 512, receives no delivery before host credit, then reassembles and
   verifies the body and settles Accepted.
3. Graviton releases a real Proton publication; Artemis redelivers it with a
   new local delivery reference before explicit acceptance.
4. Detach, End and Close complete with the real broker.
5. An independently parsed fault proxy drops Artemis's actual Disposition;
   the possible publication times out as `unknown`, with no fabricated success.

Fixtures always stop their own broker/processes and remove their temporary
instances. AMQP external-role tests here use TCP. Shared outgoing TLS trust and
hostname behavior has real Mosquitto coverage; a separate Artemis TLS
interoperability path is **NOT RUN** in this snapshot. Neither external peer
is a product dependency.

## Review repairs and complete gates

Independent cross-review found and reproduced two engine defects: admission-
ordered IDs could emit out of order across differently credited Links, and
control encoding could allocate before checking the peer frame bound. Both
have RED/GREEN regressions. IDs are now assigned at first emission without
blocking other credited Links; settlement controls preflight bounded encoding.
Further regressions cover a pending provisional ID while another delivery is
settled, interrupted known outcomes, partial/Link deadlines and timer authority.

TLS options could override the shell's passive/binary framing and write
timeouts. A failing regression established the defect; both client configs
now share the transport-owned option restrictions. The AMQP child spec captures
its creator as default observer, rather than selecting its starting supervisor.

The first full gate run passed 692 tests but failed architecture analysis:
the syntax analyzer mistook a pure local `cancel_timer/2` for Process. The
repair resolves local calls/captures by module, name and arity, including
guards/defaults and nested/sibling scopes. Existing real Process/Kernel/Erlang
and namespace checks remain enforced; compiler xref analysis is unchanged.
Independent review reran 28 architecture tests and additional scope vectors
with no blocking finding.

## Limits and next stage

The profile is volatile, non-dynamic, nontransactional format-zero messaging,
raw AMQP without SASL, unsettled senders and receiver-first settlement, without
reconnect or Link/session resumption. Arrays remain symbol-only and application
properties bounded to supported simple values. Full mandatory/conditional
selected-profile conformance is not claimed. Memory outcomes are not disk
durability; process/VM crash recovery is **UNIMPLEMENTED**, not inferred from
socket cleanup or Artemis redelivery.

G4 now requires an actual Queue.Machine/effect runtime and our memory AMQP
broker against Qpid Proton, including credit, transfer, settlement, release/
redelivery and disconnect responsibility. G5–G7 retain protocol completion,
MQTT QoS2, WAL/recovery, all four peer paths in CI, limits/model/fuzz/soak and
installation qualification. No branch/worktree, commit, push, release,
publication or deployment occurred.
